# Contractor Dashboard Training

Two ways a contractor learns the dashboard, built on the same source of truth.

1. **Interactive walkthroughs** — guided overlays that run on the contractor's
   real dashboard, in their own account, on live data. Primary.
2. **Screen recordings** — short silent captioned clips of those same
   walkthroughs, generated by driving the app with Playwright against invented
   data. Secondary.

The reason there are two and not one is bandwidth and nerves: a contractor
sitting in their car before a first job wants to watch, and a contractor
staring at a checklist they don't understand wants to be pointed at things.

## Why the interactive version is the primary one

It cannot go stale. The overlay finds its target by querying the DOM for
`[data-tour="..."]` on whatever screen the contractor is actually looking at.
If a button moves, the spotlight moves with it. If a button is deleted, the
step falls back to describing it in words and `npm run tours:verify` fails in
CI until somebody fixes the catalog — so the failure surfaces at build time
rather than in front of a contractor.

A recorded video has the opposite property: it is correct on the day it is
made and silently drifts from then on. That asymmetry is why the recordings
are the secondary channel, why they carry freshness metadata, and why the
generation script — not a file in a folder — is what we treat as the artifact.

## The moving parts

| Path | What it is |
| --- | --- |
| `src/lib/tours/catalog.ts` | The seven walkthroughs: titles, steps, copy, versions. The single source of truth for content — the overlay and the recorder both read it. |
| `src/lib/tours/anchors.ts` | The `data-tour` anchor registry. Every id here must be rendered by a real component, and every step must point at an id here. |
| `src/lib/tours/progress.ts` | Where a contractor stands, and what that means: resume points, re-offer rules, admin standings. Pure functions, no I/O. |
| `src/lib/tours/recordings.ts` | The manifest as the app sees it, plus the freshness comparison. |
| `src/components/tour/` | The engine: provider, spotlight overlay, launcher, suggestion prompt, training-page player. |
| `src/app/api/cleaner/tours/route.ts` | Progress read/write. Exists because `app_settings` is admin-only under RLS, so the settings can't be read from the browser. |
| `scripts/tours/` | Demo fixtures, request mocks, source hashing, the recorder, the publisher. |
| `scripts/verify-contractor-tours.ts` | The check that keeps all of the above honest. |

## Adding or changing a walkthrough

1. Add the `data-tour` anchor to the real component with `tourAnchor(TOUR.x)`.
   Register the id in `anchors.ts` first — the verify script fails on anchors
   that exist in one place but not the other, in both directions.
2. Write the step in `catalog.ts`. Every anchored step needs `fallback` copy:
   it's what the contractor reads when the step can't reach its screen, which
   happens routinely for the token-linked job pages.
3. **Bump the walkthrough's `version`** if the change means somebody who
   already finished it saw something different. That re-offers it to them
   (subject to the admin setting) and marks their completion as "older
   version" rather than pretending it still counts.
4. `npm run tours:verify`.
5. Re-record if a clip exists for it: `npm run tours:record`.

Bumping the version is the step people skip. The cost of skipping it is a
contractor who was told the old thing and reads as fully trained.

## Recording

```bash
npm run dev -- --port 3100          # the recorder drives a real dev server
npm run tours:record                # writes the clips + captions + manifest
npm run tours:publish               # uploads to the private storage bucket
```

The recorder signs into a fabricated contractor account and intercepts every
Supabase call, answering from `scripts/tours/demo-contractor.ts`. Requests to
any other host are blocked outright rather than allowed through, so a missing
mock shows up as a failed recording instead of a quiet call to production.
All names, addresses, phone numbers, and emails in the fixtures are invented
(`@example.test`, `555-01xx`, non-existent street numbers), so **no real
client, contractor, or payment data can appear in a clip** — which matters
even though the clips sit behind auth in a private bucket.

Each clip is a capture of the real interactive walkthrough being driven
through the real Help menu. That's deliberate: it means the video content
can't drift from the walkthrough content, because there is only one copy of
the content. Captions are WebVTT sidecars with cue timings measured from when
each step actually appeared on screen, and the recorder reads each card's
rendered text, so a step that fell back to its `fallback` copy gets a caption
matching what the clip shows rather than what the catalog hoped for.

The `.webm` and `.vtt` files are gitignored. What's committed is
`src/lib/tours/recordings.manifest.json` — the index the app reads, including
how long each clip is and what the screens looked like when it was captured.

## How freshness is decided

Three committed facts, no request-time filesystem access (source files don't
exist in a deployed bundle):

- `scripts/tours/sources.ts` declares which files each walkthrough depends on.
- `tours:record` stamps each clip with those files' content hashes.
- `tours:verify` writes the *current* hashes to
  `src/lib/tours/source-hashes.generated.json`.

When the two disagree, the clip is showing a screen that has since changed.
The contractor-facing player says so on the card, and the admin panel lists
which clips need re-recording.

Staleness is a **warning** in `tours:verify`, not a failure. A failure would
mean any UI tweak requires re-recording seven videos before it can merge, and
a check that expensive gets deleted or bypassed within a month. A warning that
is also visible in the admin UI gets acted on.

## What is deliberately not built

- **No blocking.** Every walkthrough is skippable at every step, progress is
  saved, and a skip is treated as an answer rather than something to re-ask.
  Nothing in the engine can prevent a contractor from starting work.
- **No scoring.** Completion is stored and shown to admin as context — the
  case it exists for is "this contractor says nobody told them photos were
  required." It does not feed the Novara Score, dispatch, or pay. There is no
  trigger on `cleaner_tour_progress` and nothing joins to it. The admin
  summary is counts on purpose: a percentage invites a target, and a target
  turns context into a metric people manage instead of use.
- **No auto-navigation into live work.** The checklist and photo screens are
  reachable only through a per-job dispatch link, and walking a contractor
  into a real job's checklist risks a stray tap checking off work they haven't
  done. Those screens are marked `tokenScoped`; their steps describe
  themselves in words unless the walkthrough is launched from the job page
  itself, where they spotlight the real elements. For the same reason the
  overlay swallows clicks rather than passing them through to the app.
- **No new video infrastructure.** Existing contractor portal, existing
  training platform, existing Playwright tooling, existing storage.
